# x4kas - Claude Code Instructions

## Build & Check

```bash
cargo build              # compile the workspace (both binaries)
cargo fmt --all          # format (CI runs `cargo fmt --all -- --check`)
cargo clippy --all-targets -- -D warnings  # lint incl. tests (treat warnings as errors)
cargo test               # run test suite (300+ tests, all crates)
cargo run --bin x4kas -- --url ws://127.0.0.1:17110   # GUI against a node
cargo run --bin x4kas-cli -- rpc get_info             # CLI (public resolver without --url)
cargo run --bin x4kas-cli -- query run "tx last 1d where fee > 1 KAS order by fee desc limit 20"  # a query over the index on disk
```

## Architecture

Monitors a Kaspa L1 node via wRPC, connecting by URL or through the public resolver. A Cargo workspace with two binaries over one shared library:

- `crates/x4kas-core` (lib `x4kas_core`): everything below the frontends: RPC, app state, controller, polling, analytics, config, formatting. No egui and no clap.
- `crates/x4kas-gui` (package `x4kas-gui`, binary `x4kas`): the egui/eframe desktop GUI.
- `crates/x4kas-cli` (binary `x4kas-cli`): headless commands that connect, print and exit. It must not depend on egui/eframe, so it builds fast and runs on servers without a display. The CLI will grow to cover most of what the GUI shows: put the data logic in core and keep only argument parsing and printing in the CLI crate.

### Threading model

- (GUI) `main` builds a tokio multi-thread `Runtime` by hand (no `#[tokio::main]`). eframe owns the **main thread**, which must stay **outside** the runtime context: `RwLock::blocking_read/blocking_write` panic inside it. `gui::run` enters the runtime only briefly to spawn background tasks, then drops the guard.
- **Shared state:** `Arc<tokio::sync::RwLock<App>>`. The GUI takes `blocking_write` once per frame; background tasks use `.write().await`.
- **Repaint:** background writers call `app.mark_dirty()`, which invokes the injected `App.repaint` hook (`ctx.request_repaint()`). The GUI also schedules a 1s repaint so clocks and uptime tick. Don't busy-repaint.
- **Commands:** the GUI never awaits. It sends `UiCommand`s (`Connect(RemoteTarget)`, `Disconnect`, `ExecuteRpc`, `ExplorerLoad`, `QueryRun`/`QueryCancel`/`QueriesSet`, `Shutdown`, …) over an mpsc channel to the controller task, which writes results back into `App`.
- **Connections:** exactly one active source at a time (`App.connection: ActiveConnection`): a URL or the public resolver (`RemoteTarget { url: None }`). Switching calls `Controller::stop_all` (abort polling, wait for the index writer, disconnect, `App::clear_node_data`). The chain pipeline (the address index, which carries the Dashboard's analytics incl. mining stats) only runs with a direct node (`ActiveConnection::is_direct`: a URL), not the resolver; hashrate polling and the watchlist run with either. There is no embedded node for now.
- **Chain pipeline:** one VSPC v2 fetch loop per connection (`chain_stream::run`) hands each response over a bounded channel (`SINK_QUEUE`, one response: the node sends up to 2,480 chain blocks per response) to the index writer thread (`index::task::start_writer`), which also owns the analytics engine: every batch is indexed and folded into the engine (`IndexWriter::apply` → `AnalyticsEngine::ingest`), and the engine's changed buckets are written in the same atomic batch (`index::analytics`), so the index and the Dashboard share one position and one store. A slow writer slows the fetch (backpressure); nothing is dropped. Progress is `app.chain` (`ChainStatus`: the stream's phase and catch-up, the writer's counters, `write_error`), shown as the status bar's single Analyzer chip ("Analyzing DAG (73%)" while opening, waiting, seeking or catching up, then "Analyzer synced"/"writing", or "paused"/"error"; the phase itself and its details are in the hover, which ends with a Resync button: `UiCommand::Resync` stops the pipeline, deletes the store (`index::discard`) and starts it again from scratch). The stream starts from the index's position (or the pruning point), skipped ahead to the backfill window (`StreamStart.backfill`, 24h in the GUI, `--backfill-hours` in `x4kas-cli index run`). If the store can't be opened (another x4kas process holds it), nothing runs and the chip says why. The writer publishes `app.analytics.cached_views` and `tx_histogram` after every batch. The `analytics_cache.bin` of earlier versions is imported into an empty store on first launch, then removed (`index::analytics::import_legacy_cache`).
- **Address index:** `index/` (fjall LSM store under `~/.x4kas/index/<network>/`, `FORMAT_VERSION` bumps discard it; `IndexStore::rebuilt_from` says so and the Analyzer hover shows it). Addresses are interned to `u32` ids; every data keyspace is a six-hour slab (`tx_<n>`: txid → `IndexedTx`, `atx_<n>`: an address's transactions by time with the balance delta, `btx_<n>`: a chain block's accepted transactions, `ast_<n>`: per-address stats, `apr_<n>`: counterparty deltas (`addr ‖ peer ‖ seq → PeerDelta`, one per pair per commit, stamped with `Manifest::seq`; the writer never reads them back, `query::counterparties` sums them, so a reorg's undo is a negative delta), `ptx_<n>`: each protocol's transactions by time, `ttx_<n>`: every transaction by time with a `TxSummary` (fee, mass, totals, counts, flags: the scalar properties, so a time scan filters without reading records), `blk_<n>`: hash → `BlockRecord`, `tbk_<n>`: blocks by time, `pay_<n>`: txid → the whole payload, only for payloads longer than `PAYLOAD_HEAD`, `rds_<n>`: txid ‖ input → the redeem script a P2SH spend revealed; both opt-in, see Index settings below), so pruning behind the node's pruning point (`NodeState::pruning_point_timestamp_ms`) drops keyspaces and totals are sums over slabs. The stream runs at Full verbosity, so `IndexedTx` keeps (besides addresses, amounts, fee, masses, protocol and change scores) the containing block and its time, version, lock time, subnetwork, gas, the payload's length and first `PAYLOAD_HEAD` bytes (the whole payload, up to ~250 KB, is in `pay_<n>` when kept: `Slab::payload` reads it, the `payload` query field and the transaction page use it), per-input/output script classes, covenant counts, sig ops and the covenant-era opcode flags (`tx_inspect::OpcodeUsage::to_bits`). **Block records** (`BlockKind`): a chain block gets its header fields from its VSPC entry and its own coinbase one chain block later (under its child: the node accepts only the selected parent's coinbase per chain block), which names the block's miner (the coinbase *payload's* script, `tx_inspect::coinbase_miner_address`; the outputs pay the mergeset blues' miners and are kept as `payouts`), tag, node version, subsidy; a merged block is known only through the accepted transactions it holds (verbose `block_hash`/`block_time`): time, merging chain block, accepted tx count/mass/fees, no header or miner. Records live in the slab of the block's own time and are upserted through the writer's `BlockOverlay`; a reorg removes the chain block's record and reverses the counts of the blocks its transactions were in (coinbase facts stay). The `analytics` keyspace (one key per engine bucket and one per block of the last minute, written only when `Ingest::recent_added`/`recent_removed`/`touched`/`removed` say so; block summaries keep their top `MAX_ADDRESSES_PER_BUCKET` addresses like buckets) isn't slabbed: the engine prunes it by its own windows. A VSPC response is committed in atomic chunks of `COMMIT_BLOCKS` chain blocks (removed blocks first), each advancing the manifest; removed chain blocks are reverse-applied; already-indexed chain blocks are skipped, so replays are harmless. The writer is a blocking thread (`PollingHandles::index`, not aborted but awaited by `stop_index` so it releases the store's single-writer lock); queries (`index::query`, incl. `block`/`BlockDetail`) are synchronous and run in `spawn_blocking` from the controller (`ExplorerLoad`, `AddressPage`). The GUI thread never touches the store. Ingest benchmark: `cargo test -p x4kas-core --release -- --ignored --nocapture bench_ingest` (~60k tx/s with clustering and block records; ~230 B/tx for script-less synthetic transactions). Test builders in `writer::testing`: `tx`, `coinbase` (a real payload), `chain_block` (stamps transactions into a synthetic merged block), `chain_block_full` (every header field), `in_block`.
- **Index settings:** `config::IndexSettings` (`~/.x4kas/index.toml`, `IndexFeature::FullPayloads`/`RedeemScripts`, both off by default) decides the opt-in data the writer keeps (`IndexWriter::set_features`, read from `App.index_settings` before every batch, like the labels; `put_opt_in` writes `pay_<n>`/`rds_<n>`, `remove_tx` always removes them). `Manifest::full_payloads_from_ms`/`redeem_scripts_from_ms` say since when a feature has been on (0 when on from the index's first commit, `None` while off). The Settings page's Index section toggles them (`UiCommand::IndexSettingsSet` saves), the CLI with `x4kas-cli index settings --full-payloads on|off --redeem-scripts on|off` (the GUI reads the file at launch). Query fields that need one (`FieldId::feature`: `payload`, `redeem_script`) are greyed out in every builder picker with `IndexFeature::off_reason` on hover (`field_option`), Run is disabled while the draft reads one, and `exec::run` refuses such a query (`Inputs::features`); with the feature on but turned on after the window's start, `ResultSet::notes` says older rows lack the data (a ⚠ chip in the Results header, `note:` lines on the CLI's stderr).
- **Explorer:** `explorer.rs` (core) and `gui/explorer.rs`. `App.explorer: ExplorerState` holds browser-like sub tabs (`ExplorerTab`: an `ExplorerPage` (`Home`, `Block`, `Address`, `Transaction { txid, block hint }`, `Lookup` for a 64-hex id that may be either, `Protocol(TransactionProtocol)` for a protocol's indexed transactions) with back/forward history; the first tab is the pinned Home (`HOME_TAB_ID`, `ExplorerTab::is_home`): never closed, and `ExplorerState::navigate` from it opens a new tab (`open_tab`) instead, `go_home` switches to it) and a bounded page cache (`cache: ExplorerPage → PageLoad` (`Loading`/`Ready(PageData)`/`Failed`), `CACHE_MAX`, oldest page neither a tab nor the info pane shows evicted; cleared by `clear_node_data`, tabs and the pane keep their pages and reload). The GUI sends `UiCommand::ExplorerLoad(page)` for the active tab's page (and the pane's) when `needs_load` and connected; the controller fills `BlockView` (`get_block` + `get_block_reward_info`, then `enrich_block`: the index's acceptance and fees per transaction), `AddressPageData` (an `AddressView` through `controller::address_view`; with the resolver only the balance, `AddressView::index_note` says why), `ProtocolPageData` (`query::protocol_transactions`, newest first, a direct node only; "Load older" sends `UiCommand::ProtocolPage`, which appends with `Page::append`, as `AddressPage` does for an address), or `TxView` (`tx_view`: the index (`query::transaction`), else the mempool (`RpcManager::mempool_entry`), else the block hint; `enrich_tx` resolves a node transaction's inputs from the index). A `Lookup` tries the block first, then the transaction, and `ExplorerState::resolve` moves the tab to the page found (the lookup caches a `Redirect`). A transaction page's block hint is load metadata, not identity (`ExplorerPage`'s `PartialEq`/`Hash` leave it out), so one transaction is one tab, cache entry and recents row; a load that failed without a hint is retried once a hint is known (`needs_load`). `parse_query` classifies search input (an address, a hex id, `protocol:<slug>` for a protocol page, else a label search). Pages are modeled on the Kaspa explorers: block header, DAG standing (chain block, blue/red, confirmations, reward, merge sets, parents/children), miner from the coinbase, transactions table; transaction status/fee/mass with inputs and outputs (change marked past `CHANGE_THRESHOLD`); the address page reuses `gui/address.rs` (`header`, `body`, `watch_card`). **Info pane:** `ExplorerState.pane: Option<ExplorerTab>` is the pane that slides in from the right edge on any tab (`gui/pane.rs`, `InfoPane`: an overlay, a foreground `Area` over the right of the area between the bars, never relayouting the tab behind it; it slides by position over `SLIDE_SECS`, and its left edge drags to resize): a tab of its own, not in `tabs`, so it has a page (`pane_page`) and a back/forward history (`pane_back`/`pane_forward`, the ◀ ▶ buttons in its title row; closing forgets it). Every address, block hash and transaction id is a link (`widgets::address`/`block_hash`/`transaction_id`, the latter also `transaction_id_in_block`): a click outside the Explorer calls `widgets::request_pane` (taken by the frame loop → `ExplorerState::open_pane`, which opens the pane with the page or navigates it there, the page it showed going into its history) and the pane draws the page's core as stacked cards (the shared `block_overview` + `block_transactions`, `tx_overview` + `tx_inputs`/`tx_outputs`, or the address header, `address::body` and, when watched, its watch card) from the same cache; the action bar (`gui/actions.rs`) under its title row; "Open in Explorer" in its title row (`widgets::request_explorer`, taken by the frame loop, which switches tabs and closes the pane) makes it a page in a new sub tab, × or Esc closes it. Every request from outside the Explorer (the pane, a right-click menu, a Cmd+click on any link: `widgets::linked_value` sends `request_explorer` with the new-tab flag) shows the page in its own sub tab (`ExplorerState::show_in_tab`: the tab already on it, else a new one); only a click inside the Explorer navigates the active sub tab: while it draws, `widgets::set_in_explorer` makes clicks navigate it, and the right-click menus offer a new sub tab and the pane (or "Open in Explorer" elsewhere).
- **Watchlist:** `watch.rs`. `start_watch` subscribes `UtxosChanged` for the enabled entries of the network (`RpcManager::watch_utxos`, resubscribing on reconnect), seeds balances, polls pending mempool activity, coalesces each notification into per-address `AddressEvent`s (`net_changes`, `build_events`) and raises alerts from `AlertRules` (`evaluate`: any activity, received/sent minimums, balance crossings, first activity after `idle_hours`; the idle rule measures from `WatchEntry::last_activity_ms`, which the task updates and saves). `UiCommand::WatchSet` saves `~/.x4kas/watchlist.toml` and restarts the task. Needs the node's UTXO index; otherwise `WatchPhase::Unavailable`. The messages of the rules an event trips are stored on it (`AddressEvent::alerts`; `read` once the user marks it read). `WatchState::events_raised` counts events so the GUI's toasts (`gui/toasts.rs`) pick up only new ones with alerts; `WatchState::unread_alerts` (events with an alert not marked read) is the count on the Activity card's "Mark all read" button (the tab strip shows no badge).
- **Clustering:** `index/cluster.rs`. The writer unions the input addresses of every transaction (common-input ownership) and any output whose change score (`change_scores`: fresh address, odd amount next to round ones, same address type as the inputs; only two-output shapes score high) reaches `CHANGE_THRESHOLD`, into a persistent union-find (`cl_parent`/`cl_size`/`cl_member` keyspaces, union by size, path compression). Guards (`may_union`): no union across different entity labels (`LabelBook::entity_name`: kas.fyi, kaspa.org and heuristic labels; the user's notes and `.kas` names are per address and don't count), none for L2 bridge protocols (Kasplex, Igra), none for covenant spends (a script-hash input whose redeem script introspects, `tx_inspect::redeem_script_opcodes`), and `MAX_CLUSTER` refuses runaway merges (counted in `ChainStatus::cluster_cap_hits`, shown in the Analyzer hover and `x4kas-cli index status`). The writer takes the current label book before every batch (`IndexWriter::set_labels`). Membership is knowledge, not activity: it isn't slabbed and reorgs don't undo it. `query::cluster` (which names the cluster, `ClusterInfo::label`, by the strongest then most common member label: `LabelBook::name_cluster`) and `AddressProfile::cluster_size` read it.
- **Flows:** `query::flows` follows counterparties (`FLOW_TOP` per node) `hops` out from an address into a `FlowGraph`; `UiCommand::AddressFlows` merges results into `App.address.flows` (`FlowState`, which also keeps `FlowGraph::collapse_chains`: pass-through addresses (one flow in, one out, not a root) folded into one edge listing them in `FlowEdge::via`; the window's "Collapse chains" toggle picks `FlowState::shown`; opened by the action bar's "Flow graph"), drawn by `gui/flows.rs` (force layout in `FlowWindowUi`, in graph space (positions relative to the graph's center) under a pan/zoom `View`: drag the background to pan, wheel or pinch to zoom around the pointer, "Reset view" or a double-click to recenter; a click expands a node once (`expanded` nodes wear a ring; the clicked node is pinned and its new counterparties are seeded fanned out on its least crowded side, settling briefly and gently (`EXPAND_STEPS`)), a right-click opens its menu (info pane, add/edit label, add to / edit / remove from the watchlist, worded by what the address has), a drag moves it and pins it (`pinned`: the simulation never moves it again, and nothing moves while a node is dragged); collapsed edges are dashed with a hop count; hovering an edge shows its amount in a tooltip anchored to the canvas's top right corner, and "Show amounts" (`Prefs.flow_amounts`) writes it over every edge; the Export ▾ menu writes JSON or CSV).
- **Transaction flow (Sankey):** `App.sankey: SankeyState` (the transaction on show, its `TxView`, for each output the id of the indexed transaction that spent it, and a back/forward history of its own), filled by `UiCommand::TxSankey { txid, block_hint }` (`tx_view` as the Explorer's, then `query::spenders`: for each output, the output address's transactions from the spent transaction's time on are read until one spends the outpoint, up to `SPEND_SCAN_MAX` per address, else `None`), drawn by `gui/sankey.rs` (`SankeyWindowUi`, a modal window opened by "Transaction flow" in a transaction page's Open ▾ menu: inputs on the left (or one "Block reward" node), outputs and the fee on the right, the transaction as a bar between them, ribbons (meshes eased between the bars) as wide as the amounts; a click on an input follows it to its creating transaction, on an output to its spender when known, a right-click shows the address's info pane; ◀ ▶ buttons and the history shortcuts walk the window's history).
- **Peel chains:** `index/peel.rs`. `peel_chain` walks single-input two-output spends by outpoint, backwards through `prev_txid` and forwards by finding the link-shaped spend of either output (only the unspent last remainder is picked by change score), up to `MAX_PEEL_LINKS`; `AddressProfile::peel_chain` (`PeelChain`: links oldest first, the address's 1-based `position`, `peeled_total`) is shown on the address page (pane or Explorer) and in `address profile`. Chains need `MIN_PEEL_LINKS` spends; an address with more than a few transactions is a wallet, not a link.
- **Export:** `index/export.rs`. CSV (hand-rolled RFC 4180, amounts in sompi and KAS, `time_utc` via `format::format_utc`) and JSON of an address's transactions (`all_transactions` pages through everything, `EXPORT_MAX_ROWS`) and of a flow graph (edges, with labels and `via`); JSON of a block as the Explorer shows it (`block_json`). `UiCommand::Export(ExportRequest)` writes to `export_path` under `~/.x4kas/exports/` in `spawn_blocking` and reports in `App.address.export` (`ExportStatus`, shown under the transactions table and in the flow window); the CLI prints the same text (`address txs --all --format csv`, `address flows --collapse --format csv`).
- **Queries:** `query/` (core): a structured model (`Query { entity, filter, range, group, order, limit, columns }`, `Filter` as And/Or/Not/Cond trees, `Condition { field, op, value }`, `TimeRange`, `GroupBy`), the field catalog (`fields.rs`: one `FieldSpec` per `FieldId` with its text name, kind (`FieldKind` decides the operators and literals), cost (`Summary` from the time index's `TxSummary`, `Record`, `Lookup` for labels/clusters/watchlist, `Node` for the balance column only), category and doc; four entities: `tx`, `blocks`, `payouts` (one row per chain-block coinbase output: blocks mined per pool), `addresses`), the text form (`text.rs`: `tx last 6h where fee_rate > 10 and protocol in (krc, kns) and not is_coinbase order by fee desc limit 200 select time, txid`; a hand-written tokenizer and recursive-descent parser with positioned `QueryError`s and nearest-field suggestions, and `print` for the canonical form (range before `where`, bare bool for `= true`, exact KAS decimals, durations largest unit first); `parse(&print(q)) == q`, property-tested), the executor (`exec.rs`: `plan` picks the access path from the top-level conjuncts (txid, address/sender/receiver via `atx`, accepting block via `btx`, protocol via `ptx`, else the `ttx` time scan evaluating `Summary` conditions without reading records; blocks by hash or the `tbk` scan; payouts from chain-block records; addresses by id, from the label book/watchlist, or a merge of every slab's `ast`), reads through one fjall snapshot, evaluates each `and`'s conditions cheapest first, keeps the top `limit` rows (`TopK`) or streams groups (`count`, `count_distinct`, `sum`, `avg`, `min`, `max` by fields or `time(1h)` buckets), stops early when the scan order is the asked order, and reports `scanned`/`matched`/`truncated`/`partial` (`ScanCap`, `Budget`, `Cancelled`, `AddressCap`, `GroupCap`) in a `ResultSet` of typed `Cell`s with `Column`s; `RunControl` carries the cancel flag, deadline and progress callback), and the saved queries (`saved.rs`: `~/.x4kas/queries.toml`, each `SavedQuery` storing the *text* as the canonical form (a broken one is kept with its error), plus built-in `presets()`). Multi-valued fields (`address`, `sender`, `receiver`, labels, `parents`, `pays`, `category`) match when any value does (`!=`/`not in`: none). `export::result_csv`/`result_json` write a result. GUI: the Query tab (`gui/query.rs`, `App.query: QueryState`: the run in progress with its generation and cancel flag (`start`/`progress`/`finish` drop stale answers; a cancelled run becomes `cancelled: CancelledRun`, shown until the rows it had found arrive and replace the result), the last `ResultSet` with the saved query it was run as (`result_name`, from `UiCommand::QueryRun { query, name }`) and `result_seq` (bumped per new result, so the tab resets its client-side sort), the saved queries, `watch_status` per watched query, and a `preload` (+ `preload_id` for a saved one) handed in by "Query transactions" on an address (`widgets::request_query`/`request_saved_query`, taken by the frame loop) or a block's "Query accepted transactions"/"Query blocks by this miner" (all time)). The controller runs `exec::run` in `spawn_blocking` (`query_task`, cancelled and awaited by `stop_all`/`resync` before the store closes, since a run pins it), throttles progress to `app.query`, marks the run `fetching_balances` while it fills an address result's `balance` column from the node (`fill_balances`), and, with no store open, reports why from the chain phase (`index_not_open`). `queries_set` merges in queries another process (the CLI) added to the file since the list was loaded, then writes it. CLI: `x4kas-cli query run|list|save|rm|fields|explain|watch`.
- **Query alerts:** `query/watch.rs`. Saved queries with `watch` set (`QueryWatch { enabled, every_secs, notify }`, the save dialog's Watch section) are re-run by a task started with the chain pipeline (`start_query_watch`, `PollingHandles::query_watch`, stopped and awaited by `stop_index` before the writer): every `POLL` it checks the index position and, when it moved, runs each due query over the time since its last run plus an overlap (`watched_query`; address queries run as saved and are told apart by address, their first run only seeding) and pushes rows not seen before (`Seen`, bounded, seeded on start from the events already in `App.query.events` so a reconnect doesn't raise them again) as `QueryEvent`s into `App.query.events` (`push_event`, `events_raised`, `unread`, `mark_all_read`, `clear_events`); each run's outcome (last run, error, row count) goes into `App.query.watch_status` (`QueryWatchStatus`), which the sidebar row shows on hover (red when failing). A grouped query has no row id and can't be watched (the dialog says so). The GUI toasts them (`gui/toasts.rs`, unless the watch is silent) and the Query sidebar lists them with read marks and an unread badge per query; `x4kas-cli query watch [names…]` runs the pipeline headlessly and prints them as JSON lines.
- **Labels:** `labels.rs`. `App.labels: Arc<LabelBook>` (replaced as a whole on change): user labels (`~/.x4kas/labels/user.toml`) over kas.fyi tags over the api.kaspa.org list (fetched in bulk on launch and every `REFRESH_EVERY` by `start_label_refresh`, `RETRY_AFTER` after a failure, progress in `App.label_refresh`; cached in `labels/kaspa_org.json` so the last list shows until the fetch lands; nothing is bundled with the build) over KNS `.kas` names over heuristics (`LabelSource::rank`). Heuristic labels are derived locally and never saved: the burn address of every network (`emission::burn_address`), and "Mining pool (<coinbase tag>)" for a payout address once the analytics sink has seen it mine `POOL_MIN_BLOCKS` coinbases (`MinerTally`, fed by `analytics::coinbase_miners`). A `Label` also carries kas.fyi's `link` and `categories` when known. kas.fyi (needs an API key) and KNS are per-address lookups that reveal the address, so they're opt-in (`LabelSettings`, `~/.x4kas/labels/settings.toml`), run only from the CLI (`x4kas-cli labels online`; the GUI has no online lookup) and cached with negatives for `ONLINE_TTL` (`online_cache.json`). The GUI puts the book into egui data each frame (`widgets::set_labels`) so `widgets::address` can show a label chip after the address anywhere; a click on the chip (or "Add/Edit Address Label" in the address's right-click menu) edits the user's label in place (`widgets::request_label` → `SetLabel` from the frame loop), and the Settings page lists and maintains them.
- **Task tracking:** every background task (node polling via `create_and_start_rpc`, hashrate, the chain stream and the index writer, the watchlist, and one-off frontend requests via `PollingHandles::spawn_request` / `Controller::spawn_rpc`) is stored in `PollingHandles` so `abort_all` stops it. Never spawn an untracked task that writes `App`, or it keeps writing stale data after a switch.
- **Graceful quit:** a close request (also Cmd+Q, consumed in `handle_close`) is cancelled, `Shutdown(oneshot)` is sent, a "Shutting down…" modal is shown, and the window closes once the controller signals completion (disconnected, the index writer finished its last batch); after `SHUTDOWN_PATIENCE` the modal offers "Quit now".

### Module Layout

Paths below are relative to each crate's `src/`.

**x4kas-gui**

- `main.rs`: entry point. Parses `Args` (`--url`, `--network`, `--refresh-interval-ms`), builds the runtime, calls `gui::run`. Windows release builds use the `windows` subsystem (no console window). The window (set up in `gui::run`, its dock/taskbar icon `assets/icon.png`) opens at 1280×820 and can't go below 1200×750 (`with_min_inner_size`): every layout is checked down to that size, and the column helpers wrap below their minimum widths rather than overflow.
- **Persistence:** eframe's `persistence` feature is on, with `~/.x4kas/gui.ron` as the store: the window's size and position and egui's memory (panel sizes) persist by themselves, and `GuiApp::save` keeps `Prefs` (the active tab, the analytics cards' time windows, whether the Explorer's recents pane is open, the flow graph's "Show amounts", whether the Query tab's sidebar is open; the windows are saved as a list so a saved shorter one still loads after a panel is added), restored in `GuiApp::new`. Everything else the app remembers lives in its own files under `~/.x4kas` (connection, watchlist, labels, saved queries, index settings).
- `gui/mod.rs`: `GuiApp` (`eframe::App`). Frame loop, top bar (brand, pipe-separated tab strip (`tab_button`) that highlights on hover, terminal/help/settings buttons), bottom status bar (the connection chip, whose text folds in the node's sync state ("● Connected", "◐ Connected, node syncing", "◌ Connecting to node…"/"◌ Connecting to public resolver…", a dim "◌ Connected" until the node's info arrives; a lost connection shows as connecting while the client reconnects) and whose hover lists the target, the node's details, the last poll and any error; the Analyzer chip; network; DAA score colored by lag behind the DAG tip, dimmed while paused; pause), keyboard shortcuts, quit handling. The window is created transparent with an opaque `clear_color` (macOS otherwise draws its frame's light highlight line over the top bar, which replaces the title bar).
- `gui/dashboard.rs`: Dashboard tab, modeled on the Kaspalytics home page. Layout and the node-backed cards. **x4kas-cli**

- `main.rs`: `#[tokio::main]` entry point. Global clap args (`--url`, `--network`, `--timeout`, usable before or after the subcommand) and the `Command` enum, one variant per command group.
- `rpc.rs`: `x4kas-cli rpc <method> [args…]`. `RpcCall` implements clap's `Subcommand` by hand, generating one subcommand per `RPC_METHODS` entry (positional args; a trailing list takes several words), so the CLI and RPC Cmds tab never drift. `run` validates args (`RpcMethod::validate_args`), connects (`RpcManager::connect_once`; resolver attempts retry until `--timeout`, since it sometimes hands out a dead node), and prints `rpc_json` untruncated.
- `query.rs`: `x4kas-cli query run "<text>"|--saved <name or template slug> [--format table|json|csv] [--limit]` (exit codes: 0 complete, 1 run error, 2 parse/validation error with a caret at the character column, 3 stopped early (`ResultSet::partial`) with advice on stderr; the stderr summary notes a clamped limit and shortened ids; the `\r` progress only on a terminal), `list`, `save <name> <text> [--description] [--pin] [--watch [secs]]` (takes effect in the GUI on its next launch), `rm`, `fields [entity]` (kinds via `FieldKind::describe`), `explain <text>` (the canonical text and the plan), `watch [names…] --url [--backfill-hours] [--progress]` (the headless pipeline plus the watched queries, events as JSON lines with `row` keyed by column name). `run` and `explain` open the index with `IndexStore::open_existing` (read as it is: never rebuilt, no lock wait). `index.rs` exposes `start_pipeline`/`stop_pipeline` for it.

## Conventions

- Releases: pushing a `v*` tag (matching `[workspace.package] version`) runs `.github/workflows/release.yml`, which builds `x4kas` and `x4kas-cli` for macOS (arm64, x86_64), Linux (x86_64, arm64, on Ubuntu 22.04) and Windows (x86_64), packs them as `x4kas-<tag>-<target>.tar.gz`/`.zip` (on macOS the GUI as `x4kas.app`, `scripts/macos-app.sh`) with one `SHA256SUMS` file and drafts a GitHub release (a pre-release for 0.x). Running it by hand builds without releasing. Keep the README's install section in step with the archive names.
- Run `cargo fmt --all`, `cargo clippy --all-targets -- -D warnings` and `cargo test` after changes. Tests cover app state, config, types, formatting, analytics and CLI parsing. GUI code is not unit-tested.
- Shared dependency versions live in the root `[workspace.dependencies]`; crates use `dep.workspace = true`.
- Keep async and RPC work out of `gui/`. Add a `UiCommand` and handle it in the controller instead.
- GUI and CLI share core code. Don't put data fetching or computation in either frontend crate.
- Background code that mutates `App` must call `app.mark_dirty()` so the GUI repaints.
- The chain pipeline is one store and one status: anything derived from the chain stream goes through the index writer (`IndexWriter::apply`, persisted in the same batch) and reports in `App.chain`, never a second task with its own cache or indicator.
- GUI-only view state (popups open, help or Settings visible) lives in `GuiApp` or egui memory, not `App`, unless tests need it.
- All RPC types have UI-friendly wrapper structs in `rpc/types.rs`. Don't use raw kaspa types in UI code.
- Show every Kaspa address with `widgets::address`, every block hash with `widgets::block_hash` and every transaction id with `widgets::transaction_id`, never a plain label. A click on any of them calls `widgets::request_pane` with its page; the frame loop in `gui/mod.rs` opens it in the info pane (`pane::InfoPane`, `App.explorer.pane`), which slides in on the right of any tab and loads the page through the Explorer's cache (`ExplorerLoad`). Inside the Explorer tab a click navigates the sub tab instead. An address's right-click menu adds, edits or removes the user's label and opens the address in an explorer, and its label chip edits it in place (Enter saves, Esc cancels); label changes go through `widgets::request_label` and `SetLabel`.
- The index store is synchronous and single-writer: never open it on the GUI thread or in an async task without `spawn_blocking`; the controller owns the `Arc<IndexStore>` and query tasks borrow it.
- Dashboard cards are skeletons: they always draw every row ("—" via `or_dash` until the data arrives) and list tables keep a fixed-height body (`wide_table`, with a message row while empty), so nothing jumps as data loads. Don't swap a card's contents for a one-line placeholder, except for a lasting state such as "Disabled when using the public resolver".
- Use `theme::*` colors and `widgets::*` helpers for a consistent look; never hard-code `Color32`s in views. Row labels (`field_label`) use `theme::LABEL`; other secondary text uses `.weak()`. All text is already monospace, so don't add `.monospace()`.
- Shortcuts are ignored while a text field or the terminal has focus (`ctx.wants_keyboard_input()`, `TerminalPane::has_focus`), except Ctrl+`, and, from a text field (modifier combinations type nothing), the history shortcuts and the Explorer's Ctrl+T/W/L; while a window (Help, Connection, a dialog, the transaction flow, flows, the Query tab's save dialog) is open only Ctrl+` and `?` work (the transaction flow window reads the history shortcuts itself). Esc closes exactly one thing (`GuiApp::esc_target`): a focused field or an open menu keeps it (egui clears focus before the frame, so `esc_taken` remembers the previous frame), else the topmost window (Help, Connection, a dialog, the transaction flow, flows; `modal_window` takes `close`, and draws in `Order::Foreground` so windows sit above the info pane), else the info pane, else Settings.
- Shortcuts: `1`–`6` tabs, Ctrl+Tab / Ctrl+Shift+Tab cycle, `p` pause, Ctrl+` terminal, `?`/F1 help, Esc closes one thing, Cmd+Q quits gracefully, Cmd+[ / Cmd+] (Alt+arrows, the mouse's back/forward buttons) go back/forward through the info pane's history when it is open, else the Explorer tab's (`history_navigation`); on the Explorer tab Ctrl+T / Ctrl+W / Ctrl+L (Home with the search focused (a search from Home opens a new sub tab), close, focus the search with its text selected); on the Query tab Cmd/Ctrl+Enter runs the query.
- 36 read-only RPC methods (listed in `rpc/methods.rs`) are available in the RPC Cmds tab and as `x4kas-cli rpc <method>` (lists are comma-separated). Responses are pretty-printed JSON (`to_json`; wrap bare values in a `json!` object). To add one, add it to `RPC_METHODS` and a match arm in `RpcManager::rpc_json`; a test checks every method has an arm. It then appears in the CLI (`x4kas-cli rpc <method>`) automatically. State-changing calls (`submit_*`, `add_peer`, `ban`/`unban`, `resolve_finality_conflict`, `shutdown`) are intentionally not exposed.
